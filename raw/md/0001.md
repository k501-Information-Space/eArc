**Repository State**

K501-AIONARC is currently a small, test-backed Python kernel prototype. The strongest implemented path is: immutable transition records -> append-only journal -> replay/projection -> audit -> proof -> receipt -> archive. The package has many planned directories (`api`, `agent`, `workers`, `governance`, `retrieval`, `graph`, `embeddings`, `observability`) but most are placeholders today.

Verification: `uv run pytest -q` passes: `118 passed`. Plain `pytest -q` fails because the `src/` package is not on the import path unless run through `uv`.

**Architecture Layers**

1. **Ontology/Core Model Layer**
    
    Thin Pydantic models define the ontology vocabulary: `Axiom`, `Kernel`, `Frame`, `StateObject`, `Snapshot`, `Freeze`, `Archive`, `Lifecycle`.
    
    These are mostly structural contracts. For example, [TransitionV2 (line 10)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/transition_v2.py:10) is the central domain event shape, while [StateObject (line 6)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/state_object.py:6), [Frame (line 6)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/frame.py:6), and related classes are simple immutable records.
    
2. **Identity/Canonicalization Layer**
    
    Deterministic identity is based on canonical JSON plus SHA-256. `TransitionV2.create()` hashes `before_state_id`, `after_state_id`, `transition_type`, `content`, and `provenance_transition_ids`, while deliberately excluding `timestamp_ns` and `metadata` [transition_v2.py (line 48)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/transition_v2.py:48).
    
    That means identity represents semantic transition content, not observation time or operational metadata.
    
3. **Runtime Layer**
    
    Runtime classes are pure-ish functions over transition streams:
    
    - `ReplayRuntime` folds transition content into a dict.
    - `ProjectionRuntime` derives a `StateObject` from the latest transition.
    - `SnapshotRuntime` materializes latest or point-in-time state.
    - `FreezeRuntime` hashes a snapshot into an immutable freeze artifact.
    - `AuditRuntime` validates transition ordering, state linkage, provenance references, and snapshot/freeze consistency.
    - `ProofRuntime`, `ReceiptRuntime`, and `ArchiveRuntime` produce proof-chain artifacts.
4. **Storage Layer**
    
    The real persistence primitive is [JournalStore (line 23)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/storage/journal.py:23): a JSONL append-only transition log with a persisted `head.json`.
    
    - `transitions.jsonl` is authoritative.
    - `head.json` stores `last_valid_offset`, `record_count`, and `last_transition_id`.
    - `IndexStore` is explicitly rebuildable/disposable.
    - `ArchiveStore` writes one JSON file per archive.
5. **Evidence/Proof Layer**
    
    `src/k501/evidence/*` contains simple evidence schema objects: `Proof`, `Receipt`, `Audit`, `Index`, `Pointer`. The operational proof chain actually lives in `core/*_runtime.py`.
    
6. **Documentation/Manifestation Layer**
    
    `docs/proofs/*.md` are hand-authored proof records tied to historical commits/tags/test status. These are not generated from the runtime proof system and some are stale against the code.
    

**Runtime Flow**

The intended live flow looks like this:

1. A caller creates a `TransitionV2`.
2. `JournalStore.append_transition()` validates the transition identity, rejects duplicate IDs, fsyncs a JSONL record, updates in-memory seen IDs, and persists `head.json` [journal.py (line 146)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/storage/journal.py:146).
3. `read_transitions()` streams the journal back as `TransitionV2` objects.
4. `ReplayRuntime` or `ProjectionRuntime` reconstructs current state.
5. `SnapshotRuntime` captures the latest state.
6. `FreezeRuntime` hashes the snapshot into a freeze artifact.
7. `AuditRuntime.audit_with_freeze()` validates lineage plus snapshot/freeze agreement [audit_runtime.py (line 57)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/audit_runtime.py:57).
8. `ProofRuntime.build()` hashes audit facts into a proof [proof_runtime.py (line 8)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/proof_runtime.py:8).
9. `ReceiptRuntime.build()` creates a receipt.
10. `ArchiveRuntime.build()` creates an archive payload, and `ArchiveStore.save()` persists it.

There is no implemented API/server/worker orchestration path yet; this is currently a library-level flow exercised by unit tests.

**Storage Model**

The storage model is event-sourced and file-backed.

The journal is the source of truth. It validates every stored transition during scan, reconstructs `_seen_ids`, and writes a compact head record. Indexes are accelerators, not authority. Archives are separate JSON payloads addressed by `archive_id`.

Strengths:

- Simple append-only model.
- Deterministic transition IDs.
- Rebuildable index.
- Atomic-ish head update through temp file replace.
- Tests cover basic append/read/duplicate/index behavior.

Weaknesses:

- No locking or concurrency control.
- No tail-corruption recovery despite `TailCorruptionError` existing.
- Journal scan raises on malformed tail rather than truncating to `last_valid_offset`.
- Archive writes are not fsynced/atomic.
- `IndexStore` is in-memory only.
- Archive IDs are used directly in filenames, including `archive:` prefixes.
- Some tests write to fixed `/tmp/archive-store`, which can leak state across runs.

**Lineage Model**

There are two lineage concepts:

1. **Transition lineage**
    
    `TransitionV2` has `before_state_id`, `after_state_id`, and `provenance_transition_ids`. `AuditRuntime` enforces a linear state chain by requiring each transition’s `before_state_id` to equal the previous transition’s `after_state_id` [audit_runtime.py (line 93)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/audit_runtime.py:93). It also requires provenance references to point to earlier transitions in the same stream.
    
2. **Proof lineage**
    
    `ProofGraphRuntime` builds a mapping of `proof_id -> provenance_proof_ids`. `LineageQueryRuntime` can find ancestors, root, and trace.
    
    Important limitation: although the graph type allows multiple parents, traversal follows only `parents[0]`. So the implemented lineage query model is a deterministic chain walk, not full DAG ancestry.
    

**Proof System**

There are two proof systems side-by-side:

1. **Runtime proofs**
    
    `AuditRuntime` validates transition-stream consistency. `ProofRuntime` hashes selected audit facts into a `proof_id` and includes `audit_hash`, `state_id`, and `transition_id`. `ReceiptRuntime` hashes proof/state/transition into a receipt ID. `ArchiveRuntime` hashes receipt/proof/state into an archive ID.
    
2. **Docs proofs**
    
    `docs/proofs/proof_v0_*.md` are manual manifestation records with commit/tag/test evidence. They document historical verification of ontology objects but are not connected to runtime artifacts.
    

The proof chain is promising, but not fully connected: `ReceiptRuntime.build()` expects `proof["timestamp_ns"]` [receipt_runtime.py (line 35)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/receipt_runtime.py:35), while `ProofRuntime.build()` does not emit `timestamp_ns` [proof_runtime.py (line 43)](/home/matsch/Projekte/k501-aionarc_mirror/src/k501/core/proof_runtime.py:43). So the nominal `audit -> proof -> receipt` pipeline breaks unless the caller manually injects a timestamp.

**Technical Debt**

Highest priority:

- `ProofRuntime` and `ReceiptRuntime` contract mismatch around `timestamp_ns`.
- Two transition systems exist: legacy `Transition` and newer `TransitionV2`. Several modules/tests still cover both, which creates conceptual drift.
- Proof docs are stale/manual; for example `proof_v0_state_object.md` lists `title` and `description`, but `StateObject` has `frame_id`, `version`, and `status`.
- Plain `pytest` fails due to packaging/import path; contributors need `uv run pytest` or editable install/test config.
- Runtime artifacts are mostly untyped `dict[str, Any]`, while ontology objects use Pydantic. This weakens contracts exactly where proof correctness matters.

Medium priority:

- `AuditRuntime` verifies linkage but does not validate transition identity itself.
- Snapshot/freeze verification checks IDs but does not re-hash freeze contents against `freeze_id`.
- Proof graph traversal ignores multiple parents.
- Journal lacks concurrency safety.
- Tail corruption recovery is declared but not implemented.
- Many package directories are empty placeholders.
- README is empty.
- There is a stray untracked file named `ed -n 1,200p` and several uncommitted files in the worktree.

Overall: the repository has a clean embryonic kernel for deterministic, append-only, proof-oriented state lineage. The next architectural step should be to formalize one canonical pipeline and artifact schema, then make docs/tests/API/storage line up around that single spine.
