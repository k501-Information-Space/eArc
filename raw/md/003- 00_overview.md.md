`` # K501-Aionarc Architecture Overview ## 0. Purpose of This Document This document defines the system intent, core principles, and architectural boundaries of K501-Aionarc. It is the primary reference for understanding: - What K501 is and what it is becoming - Why the architecture separates evidence, retrieval, and trust - How the core lifecycle (Axiom → Kernel → Frame → Snapshot → Freeze → Archive → Retrieval → Proof → Audit → Belief → Reasoning) works - What the three planes are and why they must not collapse into each other This is not a user guide. It is an architectural specification for engineers, researchers, and system designers. ## 1. System Identity ### 1.1 What K501 Is K501-Aionarc is a **local-first provenance operating system** with: - an **Archive Layer** for immutable preservation - a **Retrieval Layer** for controlled access - a **Governance Layer** for trust and belief management - a **Reasoning Layer** for agent action The archive is only one subsystem. Provenance is the organizing principle. This is not a better RAG system. It is a deterministic memory substrate where semantic retrieval is only one service among many. ### 1.2 What K501 Is Becoming K501 is evolving into: - a **continuity engine** for knowledge over time - a **provenance-first memory operating system** for autonomous agents - a **scientific archive engine** for auditable knowledge evolution - a potential substrate for **persistent autonomous research agents** and **long-running AI observatories** The primary object is no longer a document, chunk, vector, or prompt. The primary object is a **state transition**: ```text State A   → Snapshot  → Freeze  → Archive  → Retrieval  → State B ``` This is fundamentally different from conventional chatbot memory. ## 2. Core Design Principles K501 is built on six non-negotiable principles: ### 2.1 Local-First - All core components run locally. - No mandatory cloud dependency. - Inference is via Ollama (local LLM). - Embeddings are via `nomic-embed-text-v2-moe` (local). This enables privacy, air-gapped operation, and deterministic reproducibility. ### 2.2 Privacy-Preserving - No external data leakage. - Evidence, claims, and beliefs are owned by the local system. - Agents operate on memory they can audit. ### 2.3 Deterministic Lineage - Every state object has a stable, deterministic identifier. - Every transformation is traceable to its origin. - Lineage is explicit, not inferred. ### 2.4 Append-Only Archives - Archive records are immutable. - No in-place modification or overwrite. - History is preserved, not erased. ### 2.5 Proof-Based Validation - Claims must be validated by proof. - Proof is checked by audit. - Audit determines whether a claim can become operational belief. ### 2.6 Separation of Evidence, Retrieval, and Trust K501 separates three concepts that most memory systems accidentally merge: - **Evidence** (what exists in the archive) - **Retrieval** (what is surfaced for reasoning) - **Trust** (what can be believed and acted upon) Most RAG systems collapse these layers together. K501 keeps them conceptually and architecturally distinct. ## 3. Three-Plane Architecture The architecture is organized around three independent planes: ### 3.1 Evidence Plane The Evidence Plane is the **truth substrate**. It contains: - `Archive` - `Snapshot` - `Freeze` - `Proof` - `Audit` - `Retrieval` artifacts that are derived from evidence Properties: - Immutable - Append-only - Auditable - Replayable ### 3.2 Retrieval Plane The Retrieval Plane is the **access substrate**. It contains: - `Chunk` - `Embedding` - `Vector` - `Retrieval` results Properties: - Derivable from evidence - Upgradable without destroying evidence - Hybrid (semantic + lexical + temporal + provenance) ### 3.3 Operational Plane The Operational Plane is the **runtime substrate**. It contains: - `Kernel` - `Frame` - `Runtime` - `State` Properties: - Mutable during execution - Drives task dispatch and state transitions - Never stores evidence directly This separation is critical because it prevents retrieval infrastructure from contaminating governance and prevents runtime state from overwriting evidence. ## 4. Core Lifecycle The canonical lifecycle is: ```text Axiom   → Kernel  → Frame  → Snapshot  → Freeze  → Archive  → Retrieval  → Proof  → Audit  → Belief  → Reasoning ``` ### 4.1 Axiom The root layer that anchors deterministic origin. Formalizing this layer removes ambiguity about: - canonical state - foundation - root state - deterministic origin ### 4.2 Kernel The runtime engine that: - manages execution - dispatches tasks - creates frames - owns deterministic transitions ### 4.3 Frame An executable or observable state slice that: - carries namespace, pointer, timestamp, lineage - bridges runtime and archive ### 4.4 Snapshot A consistent view of state used for freeze. ### 4.5 Freeze A sealed immutable record of Snapshot. This is the first governance boundary where mutable state becomes historical evidence. ### 4.6 Archive Append-only storage for frozen records. ### 4.7 Retrieval Multi-signal retrieval that combines: - semantic similarity - lexical match - temporal relevance - provenance depth - proof status - audit status - belief confidence ### 4.8 Proof Validation of claims about archived content. ### 4.9 Audit Policy compliance and integrity check. ### 4.10 Belief Operational confidence state derived from evidence and validation. ### 4.11 Reasoning State-aware action by agents using trusted memory. ## 5. State Object as Universal Primitive The **State Object** is the universal memory primitive. It contains: - state_id - namespace - frame origin - snapshot origin - freeze origin - archive location - proof chain - audit chain - belief status - confidence - time anchors - retrieval links - graph links - embedding links All subsystems read and write through this object. ## 6. Reference Graph The Reference Graph is a **deterministic reference graph** for provenance and lineage traversal. It is not merely an ontology; it is a navigable structure that enables queries like: ```text Find all Frames where   Proof = P  AND Audit = passed  AND derived_from Snapshot S  AND before Time Anchor T  AND inside Namespace N ``` This is archive reasoning, not semantic search. ## 7. Evolution Stages K501 is evolving through five stages: ### Stage 1: Archive System - **Status:** completed - **Artifacts:** documents, manifests, chunks ### Stage 2: Semantic System - **Status:** building - **Artifacts:** embeddings, retrieval, ranking ### Stage 3: Provenance System - **Status:** conceptual - **Artifacts:** lineage, ancestry, derivation chains ### Stage 4: Governance System - **Status:** not built - **Artifacts:** belief, contradiction resolution, trust scoring ### Stage 5: Cognitive System - **Status:** future - **Artifacts:** autonomous reasoning, self-maintenance, memory arbitration ## 8. Current Infrastructure Status ### 8.1 Completed Infrastructure - Archive Layer: **Complete** - Manifest Layer: **Complete** - Chunk Layer: **Complete** - Validation Layer: **Complete** - Embedding Layer: **Operational** ### 8.2 Partial Infrastructure - Semantic Layer: **Early Operational** - Provenance Layer: **Conceptually Strong** ### 8.3 Missing Infrastructure - Governance Layer: **Not Yet Implemented** - Graph Layer: **Not Yet Implemented** - Belief Layer: **Not Yet Implemented** - Agent Layer: **Not Yet Implemented** ### 8.4 Maturity Summary - Archive Infrastructure: **High** - Retrieval Infrastructure: **Medium** - Reasoning Infrastructure: **Low** - Governance Infrastructure: **Low** ## 9. Bottleneck Analysis The current bottleneck is **retrieval quality**, not: - chunking - embeddings - storage - archive size Specific gaps: - Semantic Search: **partial** - Retrieval Ranking: **weak** - Provenance Ranking: **missing** - Hybrid Retrieval: **missing** ## 10. Questions This Architecture Answers K501 is designed to answer: 1. What is the state? 2. Where did it come from? 3. What supports it? 4. What contradicts it? 5. Why was it trusted? 6. Which agents may use it? 7. How does it change over time? ## 11. Relationship to Other Systems K501 is: - **More archive-centric and lineage-heavy** than LangGraph - **More deterministic, proof-oriented, and evidence-immutable** than Letta/MemGPT - **More durable-knowledge-focused** than OpenAI Agents SDK, AutoGen, CrewAI, PydanticAI, OpenDevin - **More ontology-aware and provenance-heavy** than conventional knowledge-graph RAG ## 12. Next Steps The next architectural milestones are: 1. Formalize the canonical ontology and state object. 2. Build the Reference Graph. 3. Introduce claims, validation, and belief management. 4. Upgrade retrieval to hybrid, provenance-aware search. 5. Expose the system to agents via a stable memory API. ## 13.
