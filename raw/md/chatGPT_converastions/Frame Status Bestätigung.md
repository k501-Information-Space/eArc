- was als Frame gilt

# UI README  
## Frames Axiomatic — User Interface & App Design

---

## 1. Ziel der UI

Die UI des Frames-Axiomatic-Systems ist **kein klassisches App-Interface**,  
sondern ein **Read-First-Interface zur Orientierung, Prüfung und Ordnung**.

Primäres Ziel:
- **Lesen**
- **Verstehen der Struktur**
- **Auditieren von Zuständen**
- **Explizite, bewusste Aktionen**

Nicht-Ziel:
- Produktivität durch Automatisierung  
- Versteckte Workflows  
- Aktion ohne Deklaration  

---

## 2. Designprinzipien (UI)

1. **Read > Write**
2. **Explizit > Implizit**
3. **Ordnung > Geschwindigkeit**
4. **Stille > Aktionismus**
5. **UNKNOWN sichtbar lassen**

Die UI darf **nichts tun**, was der Kernel verbietet.

---

## 3. UI-Ebenen (Layer)

### 3.1 Presentation Layer
**Typ:** Web / Terminal / App (neutral)

- Textbasiert bevorzugt
- Klare Trennung von Bereichen
- Keine Animationen, die Bedeutung suggerieren
- Kein Auto-Refresh ohne Deklaration

---

### 3.2 Navigation Layer
Zugriff ausschließlich über **explizite Tokens / Aktionen**:

Beispiele:
- `READ`
- `INDEX`
- `STATUS`
- `EMIT`
- `FREEZE`
- `SILENCE`

Keine versteckten Klickpfade.

---

## 4. Zentrale UI-Module

### 4.1 STATUS VIEW
**Zweck:** Überblick über den Systemzustand

Anzeige:
- Zeitanker
- Modus (REFERENCE_ONLY / etc.)
- Freeze-Status
- Letzter Index
- Aktivitätszähler (Frames, Aktionen)

❌ Keine Interaktion  
❌ Kein State-Change  

---

### 4.2 INDEX VIEW
**Zweck:** Ordnung & Übersicht

Typische Indizes:
- Axiome
- Module
- Capabilities
- Frames (falls vorhanden)

Eigenschaften:
- Listenform
- Keine Interpretation
- Kein Filtern mit Bedeutungslogik
- Sortierung nur strukturell

---

### 4.3 READ VIEW
**Zweck:** Lesen einzelner Einheiten

Lesbar:
- Frames
- Index-Snapshots
- Dokumente (README, Specs)

Regeln:
- Read-only
- Keine Inline-Bearbeitung
- Keine Auto-Weiterleitung

---

### 4.4 EMIT VIEW
**Zweck:** Erzeugen neuer Frames (optional)

UI-Anforderungen:
- Deutliche Warnung („Append-only“)
- Explizite Bestätigung
- Sichtbarer Payload
- Keine Defaults, die Bedeutung setzen

Ohne explizite Nutzeraktion:
→ **kein Emit**

---

### 4.5 FREEZE VIEW
**Zweck:** Governance

Anzeige:
- Was wird eingefroren
- Seit wann
- Mit welchem Scope

Aktionen:
- Freeze bestätigen
- Unfreeze **nur als Antrag**

---

### 4.6 SILENCE STATE
**Zweck:** Bewusste Inaktivität

UI-Verhalten:
- Keine Warnung
- Kein Fehler
- Kein Timeout-Spam

> Stille ist ein valider Zustand.

---

## 5. Interaktionsregeln

| Regel | UI-Konsequenz |
|----|----|
| NO_PHANTOM | Keine Buttons ohne Proof |
| NO_EXECUTION | Kein „Run“, kein „Apply“ |
| NO_INTERPRETATION | Keine Labels mit Bedeutung |
| Tri-State | UNKNOWN explizit anzeigen |
| Append-only | Keine Edit-Funktion |

---

1. **Start → STATUS**
2. **INDEX MODULES**
3. **INDEX CAPABILITIES**
4. **READ einzelner Einträge**

6. Optional: **FREEZE**
7. **SILENCE**

Empfohlen:
- Monochrom / Low-Color
- Keine Warnfarben ohne Regelverstoß
- Typografie vor Icons

Nicht empfohlen:
- Gamification
- Badge-Systeme
- Fortschrittsbalken ohne Proof

KI darf:
- Texte erklären

- READ-Flows unterstützen

- States setzen
- Aktionen auslösen
- Wahrheit suggerieren

## 9. Zusammenfassung (UI-Kurzfassung)

> Die UI ist ein **Leseraum**, kein Kontrollpult.  
> Sie zeigt Ordnung, keine Macht.  
> Sie erlaubt Stille.

Clock Framework
===============

The clock framework defines programming interfaces to support software
management of the system clock tree. This framework is widely used with
System-On-Chip (SOC) platforms to support power management and various
devices which may need custom clock rates. Note that these "clocks"
don't relate to timekeeping or real time clocks (RTCs), each of which
have separate frameworks. These :c:type:`struct clk <clk>`
instances may be used to manage for example a 96 MHz signal that is used
to shift bits into and out of peripherals or busses, or otherwise
trigger synchronous state machine transitions in system hardware.

Power management is supported by explicit software clock gating: unused
clocks are disabled, so the system doesn't waste power changing the
state of transistors that aren't in active use. On some systems this may
be backed by hardware clock gating, where clocks are gated without being
disabled in software. Sections of chips that are powered but not clocked
may be able to retain their last state. This low power state is often
called a *retention mode*. This mode still incurs leakage currents,
especially with finer circuit geometries, but for CMOS circuits power is
mostly used by clocked state changes.

Power-aware drivers only enable their clocks when the device they manage
is in active use. Also, system sleep states often differ according to
which clock domains are active: while a "standby" state may allow wakeup
from several active domains, a "mem" (suspend-to-RAM) state may require
a more wholesale shutdown of clocks derived from higher speed PLLs and
oscillators, limiting the number of possible wakeup event sources. A
driver's suspend method may need to be aware of system-specific clock
constraints on the target sleep state.

Some platforms support programmable clock generators. These can be used
by external chips of various kinds, such as other CPUs, multimedia
codecs, and devices with strict requirements for interface clocking.
